# Pré-prompt: DssSplitter

## 1. CLASSIFICAÇÃO E CONTEXTO
*   **Golden Reference**: DssChip (componente interativo)
*   **Golden Context**: O DssSplitter é um componente fundamental no Design System Sansys, projetado para oferecer flexibilidade e controle ao usuário na organização de layouts. Ele permite o redimensionamento dinâmico do espaço entre dois painéis adjacentes, possibilitando que o usuário ajuste a proporção de cada painel de forma intuitiva. Este componente é ideal para a construção de interfaces complexas que exigem alta personalização e adaptabilidade, como ambientes de desenvolvimento integrado (IDEs), painéis de administração com múltiplos widgets, ou qualquer aplicação que apresente diversas visualizações de dados simultaneamente. Sua implementação visa otimizar a experiência do usuário, permitindo que ele configure o espaço de trabalho de acordo com suas necessidades específicas, melhorando a produtividade e a ergonomia da interface.
*   **Justificativa**: A inclusão do DssSplitter no Design System Sansys é impulsionada pela crescente demanda por layouts adaptáveis e eficientes em aplicações modernas. Em cenários onde a informação é densa e a multitarefa é comum, a capacidade de ajustar dinamicamente a distribuição do espaço na tela torna-se crucial. O DssSplitter não apenas melhora a usabilidade ao permitir que o usuário controle a hierarquia visual e a área disponível para diferentes conteúdos, mas também contribui para uma experiência mais rica e personalizada. Ele endereça a necessidade de criar interfaces que respondam de forma inteligente às preferências do usuário e às variações de contexto, garantindo que o conteúdo mais relevante esteja sempre em destaque e acessível.

## 2. RISCOS ARQUITETURAIS E GATES
*   **Performance**: É imperativo garantir que o redimensionamento do DssSplitter seja executado de forma suave e responsiva, mesmo quando os painéis contêm conteúdo complexo ou interativo. A otimização deve focar em evitar reflows excessivos do layout e em otimizar a renderização para prevenir travamentos ou lentidão na interface. Mecanismos de debounce ou throttle podem ser considerados para eventos de redimensionamento, e a atualização do DOM deve ser minimizada para garantir fluidez.
*   **Acessibilidade**: O DssSplitter deve ser totalmente operável via teclado, seguindo as diretrizes da WCAG. Isso inclui a navegação por tabulação até o separador e o uso de teclas de seta (ArrowLeft/ArrowRight para horizontal, ArrowUp/ArrowDown para vertical) para ajustar a posição. É crucial fornecer feedback visual claro para o estado de foco e arrasto, além de feedback semântico adequado para tecnologias assistivas, utilizando atributos ARIA como `role="separator"`, `aria-valuenow`, `aria-valuemin`, `aria-valuemax` e `aria-orientation`.
*   **Responsividade**: O componente deve ser robusto o suficiente para se adaptar a uma ampla gama de tamanhos de tela e orientações (portrait/landscape). Em telas menores, pode ser necessário ajustar o comportamento do splitter, como desativá-lo temporariamente, converter o layout para uma pilha vertical, ou até mesmo ocultá-lo, oferecendo uma alternativa de navegação ou visualização. A estratégia de responsividade deve ser bem definida para cada breakpoint.
*   **Estado Persistente**: Em certas aplicações, pode ser desejável que a posição do splitter seja persistente entre sessões do usuário ou navegações dentro da aplicação. O Design System deve prever mecanismos para gerenciar e armazenar esse estado (por exemplo, via `localStorage` ou API de backend), garantindo que a interface retorne ao último estado configurado pelo usuário, se aplicável.
*   **Validação de Limites**: O DssSplitter deve implementar uma validação rigorosa para prevenir que o separador ultrapasse limites definidos pelos desenvolvedores ou que cause o colapso indesejado de um dos painéis. Isso inclui a manipulação de cenários onde os limites mínimo e máximo são configurados de forma inválida, garantindo um comportamento fallback robusto e previsível.

## 3. MAPEAMENTO DE API (QUASAR → DSS)
O DssSplitter visa oferecer uma API intuitiva e consistente, inspirada em padrões de componentes de UI, mas adaptada à filosofia do Design System Sansys. Abaixo, detalhamos o mapeamento de propriedades e eventos, com descrições expandidas para clareza:
*   **`model-value` (Quasar `v-model`)**: Mapeia para a propriedade `value` no DSS. Esta propriedade controla a proporção ou o tamanho do primeiro painel em relação ao segundo. Seu tipo é `Number`, e o valor pode representar um percentual (0-100) ou um valor em pixels, dependendo da configuração do componente. A alteração deste valor reflete diretamente a posição do separador.
*   **`limits` (Quasar `limits`)**: Mapeia para a propriedade `limits` no DSS. Define os valores mínimo e máximo permitidos para a propriedade `value`. É um `Array<Number>` onde o primeiro elemento é o limite mínimo e o segundo é o limite máximo (ex: `[20, 80]` para um percentual de 20% a 80%). Estes limites garantem que os painéis não se tornem excessivamente pequenos ou grandes, mantendo a usabilidade.
*   **`horizontal` (Quasar `horizontal`)**: Mapeia para a propriedade `orientation` no DSS. Esta propriedade determina se o splitter se move horizontalmente (dividindo o espaço verticalmente) ou verticalmente (dividindo o espaço horizontalmente). Os valores aceitos são `'horizontal'` ou `'vertical'`. O padrão é `'horizontal'`, o que significa que o separador se move da esquerda para a direita ou vice-versa.
*   **`reverse` (Quasar `reverse`)**: Mapeia para a propriedade `reverse` no DSS. Um `Boolean` que, quando `true`, inverte a ordem visual dos painéis sem alterar a lógica interna de `value`. Isso é útil para layouts que precisam de flexibilidade na apresentação sem reestruturar o conteúdo.
*   **`separator-class` (Quasar `separator-class`)**: Mapeia para a propriedade `separatorClass` no DSS. Permite a aplicação de classes CSS customizadas ao elemento separador, oferecendo flexibilidade para estilizações específicas que não são cobertas pelos tokens de design padrão.
*   **`separator-color` (Quasar `separator-color`)**: Mapeia para a propriedade `separatorColor` no DSS. Controla a cor do separador. Embora os tokens de design sejam preferenciais, esta propriedade oferece um controle mais granular para casos de uso específicos ou temas contextuais.
*   **`disable` (Quasar `disable`)**: Mapeia para a propriedade `disabled` no DSS. Um `Boolean` que, quando `true`, desativa completamente a interação com o splitter, tornando-o não arrastável e alterando seu estilo visual para indicar o estado de desativação.
*   **`emit-immediately` (Quasar `emit-immediately`)**: Mapeia para a propriedade `emitImmediately` no DSS. Um `Boolean` que, quando `true`, faz com que o evento de atualização de valor (`change`) seja emitido continuamente durante o arrasto do separador, em vez de apenas no final do arrasto. Isso é útil para feedback em tempo real em certas aplicações.
*   **Eventos**: O DssSplitter emite eventos para notificar a aplicação sobre interações do usuário. `update:model-value` (Quasar) mapeia para `change` (DSS), disparado quando o valor do splitter é alterado. `splitter-click` (Quasar) mapeia para `click` (DSS), disparado ao clicar no separador. `splitter-resize` (Quasar) mapeia para `resize` (DSS), disparado quando o redimensionamento é concluído.

## 4. GOVERNANÇA DE TOKENS E CSS
A estilização do DssSplitter é rigorosamente controlada por tokens de design, garantindo consistência e facilidade de manutenção em todo o Design System. A seguir, detalhamos os tokens e suas aplicações:
*   **Espaçamento do Separador**: `--dss-spacing-2` é o token padrão para definir a espessura do separador, garantindo que ele seja visualmente discreto, mas funcionalmente acessível. Para variações de tamanho, outros tokens de espaçamento podem ser utilizados, como `--dss-spacing-1` para um separador mais fino ou `--dss-spacing-3` para um mais proeminente.
*   **Cor de Fundo do Separador**: `--dss-surface-default` ou `--dss-surface-variant` são os tokens recomendados para a cor de fundo do separador em seu estado padrão. Isso garante que o separador se integre harmoniosamente com o contexto visual dos painéis adjacentes, mantendo a neutralidade e a legibilidade.
*   **Cor do Separador (Hover/Active)**: `--dss-action-hub-default` é o token a ser utilizado para a cor do separador quando o usuário interage com ele (estados de `hover` ou `active`). Este token de ação `hub` proporciona um feedback visual claro e consistente, indicando que o separador é interativo e está pronto para ser manipulado. Em casos específicos, `--dss-action-water-default` ou `--dss-action-waste-default` podem ser considerados para estados de feedback alternativos, alinhados à paleta de ações do Design System.
*   **Raio das Bordas (se aplicável ao separador)**: `--dss-radius-sm` é o token padrão para o raio das bordas do separador, caso ele possua cantos arredondados. Isso contribui para a estética geral do componente, alinhando-o com o estilo visual do Design System. Outros tokens de raio, como `--dss-radius-md` ou `--dss-radius-lg`, podem ser aplicados para variações de estilo.
*   **Duração da Transição (se houver animação)**: `--dss-duration-200` é o token recomendado para a duração de quaisquer animações ou transições aplicadas ao separador (por exemplo, transições de cor no `hover`). Isso garante que as animações sejam suaves e não intrusivas, contribuindo para uma experiência de usuário agradável.
*   **Tokens para ícones de arrasto (se presentes)**: Se o separador incluir ícones visuais para indicar a capacidade de arrasto, `--dss-icon-size-md` deve ser utilizado para definir o tamanho desses ícones, garantindo consistência com outros ícones no Design System. A cor dos ícones pode ser controlada por tokens como `--dss-icon-default` ou `--dss-icon-subtle`.

## 5. ACESSIBILIDADE E ESTADOS
A acessibilidade é um pilar fundamental no desenvolvimento do DssSplitter, garantindo que todos os usuários, independentemente de suas capacidades, possam interagir plenamente com o componente. Os estados visuais e semânticos são cuidadosamente definidos:
*   **Operação por Teclado**: O separador deve ser acessível via navegação por `Tab`, permitindo que usuários de teclado o alcancem. Uma vez focado, o redimensionamento deve ser possível através das teclas `ArrowLeft` e `ArrowRight` para um splitter horizontal, e `ArrowUp` e `ArrowDown` para um splitter vertical. A interação deve ser suave e previsível, com feedback visual claro.
*   **ARIA Attributes**: Para garantir a compatibilidade com tecnologias assistivas, o DssSplitter deve implementar os seguintes atributos ARIA:
    *   `role="separator"`: Identifica o elemento como um separador interativo.
    *   `aria-valuenow`: Indica o valor atual da posição do separador.
    *   `aria-valuemin`: Define o valor mínimo permitido para a posição do separador.
    *   `aria-valuemax`: Define o valor máximo permitido para a posição do separador.
    *   `aria-orientation`: Especifica a orientação do separador (`horizontal` ou `vertical`).
*   **Foco**: O separador deve receber e gerenciar o foco visualmente de forma proeminente, utilizando um anel de foco (`outline`) que seja claramente visível e contraste com o fundo, seguindo os tokens de foco do Design System.
*   **Estados**: O DssSplitter possui diversos estados visuais e interativos:
    *   `default`: O estado inicial do componente, onde o separador é visível, interativo e aguarda a interação do usuário. Sua estilização deve ser neutra e discreta.
    *   `hover`: Quando o cursor do mouse passa sobre o separador, um feedback visual (ex: alteração da cor de fundo, aumento da espessura, ou um ícone de arrasto) deve ser exibido para indicar que o componente é interativo.
    *   `active` / `dragging`: Durante o processo de arrasto do separador, um feedback visual mais pronunciado (ex: cor de destaque, cursor `grabbing`, sombra) deve ser aplicado para indicar que o componente está sendo ativamente manipulado pelo usuário.
    *   `disabled`: Quando o splitter está desativado, ele não deve responder a interações do usuário. Sua estilização deve indicar claramente esse estado (ex: opacidade reduzida, escala de cinza, cursor `not-allowed`), comunicando que a funcionalidade de redimensionamento não está disponível.

## 6. DEPENDÊNCIAS E COMPOSIÇÃO
A arquitetura do DssSplitter é projetada para ser modular e eficiente, minimizando dependências diretas e maximizando a capacidade de composição:
*   **Dependências**: O DssSplitter é projetado para ser um componente autônomo em sua funcionalidade principal, não dependendo diretamente de outros componentes DSS para operar. No entanto, ele pode opcionalmente integrar `DssIcon` se o design do separador incluir um ícone visual para indicar a capacidade de arrasto. Esta dependência é gerenciada de forma leve, garantindo que o componente permaneça flexível.
*   **Composição**: O DssSplitter atua como um container de layout flexível, compondo dois slots principais (painéis) que podem hospedar qualquer tipo de conteúdo. Isso inclui outros componentes DSS (como `DssCard`, `DssTable`, `DssChart`), layouts complexos, ou conteúdo HTML/Vue arbitrário. A capacidade de compor conteúdo variado dentro dos painéis torna o DssSplitter extremamente versátil para a construção de interfaces ricas e dinâmicas. A gestão do espaço e do redimensionamento é abstraída pelo splitter, permitindo que os desenvolvedores se concentrem no conteúdo dos painéis.

## 7. EXCEÇÕES PREVISTAS
Ao projetar e implementar o DssSplitter, diversas exceções e cenários de borda foram considerados para garantir a robustez e a usabilidade do componente:
*   **Conteúdo Fluido**: Problemas de layout podem surgir se o conteúdo inserido nos painéis não for projetado para ser fluido ou responsivo ao redimensionamento. É responsabilidade do desenvolvedor garantir que o conteúdo dos slots se adapte adequadamente às novas dimensões dos painéis. O DssSplitter fornece o mecanismo de redimensionamento, mas não impõe a responsividade do conteúdo interno.
*   **Aninhamento Complexo**: Embora o aninhamento de múltiplos DssSplitters seja suportado, cenários de aninhamento complexo (por exemplo, um splitter horizontal dentro de um vertical, e vice-versa) podem levar a desafios na gestão de estado, na performance de renderização e na experiência do usuário. Recomenda-se cautela e testes rigorosos ao implementar layouts com múltiplos níveis de aninhamento de splitters para evitar comportamentos inesperados ou degradação de performance.
*   **Limites Inválidos**: Se as propriedades `limits` forem configuradas de forma inválida (por exemplo, `min` maior que `max`, ou valores fora do intervalo esperado), o componente deve ter um comportamento fallback robusto. Isso pode incluir o uso de limites padrão, a desativação temporária do splitter, ou a emissão de um aviso no console para alertar o desenvolvedor. A validação de entrada é crucial para a estabilidade.
*   **Conteúdo com Scroll**: Se um dos painéis contiver conteúdo com scroll interno, o comportamento do splitter deve ser claro para evitar conflitos de rolagem. Por exemplo, o arrasto do separador não deve ser confundido com a rolagem do conteúdo interno. Pode ser necessário ajustar a área de "pega" do separador ou a lógica de eventos para diferenciar essas interações.
*   **Interação com Drag-and-Drop**: Em interfaces que utilizam funcionalidades de drag-and-drop, é importante garantir que a interação com o DssSplitter não interfira ou seja interferida por operações de arrastar e soltar de outros elementos. A coordenação de eventos de ponteiro e a prevenção de comportamentos padrão do navegador são essenciais.

## 8. SUPERFÍCIE DE PLAYGROUND
A Superfície de Playground do DssSplitter é um ambiente interativo essencial para testar, demonstrar e documentar o comportamento do componente em diversas configurações. Ela deve permitir a manipulação de todas as propriedades e a observação dos estados resultantes.

### Controles Obrigatórios:
*   **`value`**: Um slider numérico ou campo de entrada para controlar a posição inicial do splitter. Deve permitir valores de 0 a 100 (para percentual) ou em unidades de pixel, com feedback visual em tempo real.
*   **`orientation`**: Um grupo de radio buttons ou um seletor (`select`) com as opções `horizontal` e `vertical`, permitindo alternar a direção do splitter e observar a reorientação do layout.
*   **`limits`**: Dois campos de entrada numéricos para definir os valores `min` e `max` dos limites do splitter. A interface deve validar esses valores e fornecer feedback se forem inválidos.
*   **`disabled`**: Um checkbox ou toggle switch para ativar/desativar o splitter, demonstrando seu estado não interativo e a alteração de estilo associada.
*   **`reverse`**: Um checkbox ou toggle switch para inverter a ordem dos painéis, mostrando como o conteúdo é reordenado visualmente.
*   **`emitImmediately`**: Um checkbox ou toggle switch para controlar a emissão de eventos de atualização de valor durante o arrasto, permitindo observar a diferença no comportamento de feedback.
*   **`separatorClass`**: Um campo de texto para adicionar classes CSS customizadas ao separador, demonstrando a flexibilidade de estilização.
*   **`separatorColor`**: Um seletor de cor ou campo de texto para definir a cor do separador, ilustrando a personalização visual.

### Composite Logic (Concreta, Não Genérica):
*   **Exemplo de Layout com Conteúdo Rico**: Demonstrar o DssSplitter dividindo dois `DssCard`s ou `DssContainer`s. Dentro de cada `DssCard`, incluir diferentes tipos de conteúdo, como texto, imagens, `DssButton`s e `DssTable`s, para ilustrar como o conteúdo se adapta ao redimensionamento. O objetivo é mostrar um cenário de uso real, como um painel de dashboard com um gráfico de um lado e uma tabela de dados do outro.
*   **Demonstração de Splitter Aninhado**: Apresentar um cenário onde um DssSplitter horizontal está aninhado dentro de um DssSplitter vertical (ou vice-versa). Isso permite testar e visualizar o comportamento de layouts complexos e a interação entre múltiplos splitters, por exemplo, um layout de IDE com um painel lateral redimensionável e um painel principal dividido em duas seções horizontais.
*   **Integração com Componentes de Formulário**: Mostrar como o DssSplitter pode ser usado para organizar formulários longos, dividindo-os em seções redimensionáveis, onde cada painel contém um grupo de campos de entrada (`DssInput`, `DssSelect`, etc.).
